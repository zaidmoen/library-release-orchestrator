# Live demo: `/library-release` (Phase 1)

A 10–15 minute read-only walkthrough for the engineering team. The default experience
is **one `assess` engine call** (after lightweight argument intake), producing a
≤ 8-line STATUS / WHY / NEXT card. More detail is shown only when requested.

**Safety:** This demo never publishes, pushes, merges, deploys, changes Jira, or
posts to Slack. `lab-init` creates fictional local repositories; preview/report
commands may write local output files only. Never pass `--approve`.

## What is real, and what is a fixture?

| Data | Offline Release Lab | Real library PR |
|---|---|---|
| Git commits, tags and ancestry | Real local Git history generated by `lab-init` | Real checked-out library repository and remote refs |
| Dependency evidence | Real Python AST / Git analysis over fictional FIN changes | Python AST / Git analysis of the real proposed change |
| Jira issues and `blocked_by` | Fictional timestamped `jira.yaml` snapshot | Exported ticket snapshot; **live Jira is not connected** |
| PRs | Fictional `pull-requests.yaml` snapshot, explicitly labelled as a fixture | Live GitHub PR reads; **do not set `pull_requests.snapshot`** |
| GitHub Releases | No remote; local tags only | Live releases/refs if accessible |
| Consumer impact | Fictional invoice/payment service repositories | Configured, locally cloned consumer repositories |
| Runtime validation | **Not performed by `assess`** | **Not performed by `assess`**; Phase 3 is future work |

Never present a fictional lab result as evidence about a real company release.

## One-time setup

From the **orchestrator repository**:

```bash
pip install -e .
release-orchestrator lab-init --dest ./demo
```

Open Claude Code in `demo/harri-release-lab-library`. Make the orchestrator's
`.claude/skills/library-release` directory available globally at
`~/.claude/skills/library-release`, using a symbolic link or a Windows directory
junction (or start Claude Code in the orchestrator checkout and operate on the lab).
The link must point to the **orchestrator Skill**, not to a copied or outdated copy:
its `scripts/lro.py` locates the engine from its own checkout.

The offline lab has no GitHub remote. If intake asks for a repository identity, supply
`--repository zaidmoen/zaidlibrary` **once**, which becomes
`intake.global_args` for the command. This is only an identity override: PR and Jira
data in the lab still come from **fixtures**, not live GitHub.

## Demo script: seven short scenes

The cards below describe the captured Phase 1 lab scenarios. Statuses and details
must be rechecked on a fresh lab before presenting; a cached timing is a measurement,
not a guarantee for a different machine.

| # | Engineer types | Expected outcome and talking point |
|---|---|---|
| 1 | `/library-release #15` | 🔴 **BLOCKED.** PR #15 → FIN-211 imports `currency.convert` at `invoices.py:18`, introduced by unreleased FIN-198. Static symbol evidence is confirmed; Jira's `blocked_by` link is declared snapshot data; runtime is **not verified**. The engine offers **include FIN-198** (changes scope) or **hold FIN-211** (fallback, does not meet the request), without choosing either. |
| 2 | `why?` | Expand evidence, classifications, decision log and freshness **from the same `assess` payload**, with no extra assessment call. |
| 3 | `include FIN-198` | Explicitly choose the change in release content; the existing workflow continues into Q2 (services), Q3 (optional environments), impact preview and `release-report` / copyable Slack text. All steps remain read-only **until an explicit approved write**, which this demo does not perform. |
| 4 | `/library-release FIN-204` | 🟡 **NEEDS REVIEW.** No blocking static/Jira dependency detected, but no validation run exists for this exact plan and the analysis carries a behaviour-coupling warning. **Do not call it READY.** |
| 5 | `/library-release --order v1.1.0-rc.23,v1.1.0-rc.22` | 🔴 **BLOCKED** requested order. Alternatives describe **changing the requested order** or **retiring older candidates**; reordering itself does **not add tickets**. |
| 6 | `/library-release` then `/library-release FIN-204 #15` | ⚪ Without an argument, the lab offers open PRs **#21, #19 and #15** for the engineer to choose; it never guesses. A mismatched ticket and PR becomes **CONFLICT**, not a release decision. |
| 7 | `/library-release #15` again | Repeat the same read-only assessment to demonstrate cache reuse. Phase 1's recorded Windows lab benchmark was **≈ 0.65 s warm**, with 22 Git subprocesses; observe the actual timing in `assess` JSON rather than promising that number. |

**Important distinction:** one `assess` call is the *starting assessment*, not the
entire interactive release workflow. Q2/Q3, preview and report use their existing
read-only commands after a content choice. A BLOCKED status cannot be overridden by
Claude. Even a compatible plan can remain NEEDS REVIEW until validation and
authorization evidence exist.

### Optional CLI fallback (from the library lab directory)

The same assessment surface can be shown without Claude:

```bash
release-orchestrator --repository zaidmoen/zaidlibrary assess --pr 15 --brief
release-orchestrator --repository zaidmoen/zaidlibrary assess --ticket FIN-204 --brief
release-orchestrator --repository zaidmoen/zaidlibrary assess --order v1.1.0-rc.23,v1.1.0-rc.22 --brief
```

A blocked assessment can intentionally exit with code 3, and unresolved/ambiguous
input can exit with code 5: these are release decisions, not necessarily CLI crashes.
If a needed PR or ticket is missing from the fixture, inspect its source rather than
inventing a live lookup.

After choosing a Q1 option, the existing `release-mode preview` and
`release-report` generate the impact plan and unsent Slack summary. They are
documented in [release modes](release-modes.md) and the [CLI reference](cli.md).
The previous multi-command `context → resolve-change → release-graph` sequence is
still supported for debugging, but is **not** the default engineer experience.

## Demonstrating on a real library PR

**Before the meeting**, choose a real PR and verify that the participants have
permission to read it and the related library and consumer repositories. Prepare a
read-only checkout, not a production release operation.

1. Clone the **library** repository locally with `origin` pointing to the real
   GitHub remote. Clone relevant **consumer services** locally as well; the config
   should point to those local paths.
2. Configure `release-orchestrator.yaml` in or above the library checkout. At minimum,
   confirm `library.repo`, `library.package_dir`, `library.source_ref`,
   `library.version_file`, `library.tag_prefix` (if needed), `consumers`
   (name, repo path, dependency file), environment names/branches and
   `registry: {provider: local}`. Do not configure a production registry.
3. Ensure GitHub PRs are **live**: do not set `pull_requests.snapshot`; select the
   supported live provider/configuration and use a read-only `GITHUB_TOKEN` for
   private repositories. A fine-grained token with **Contents: read** and
   **Pull requests: read** (plus the platform's implicit metadata access) is the
   minimum starting point; organization rules may require more read permissions.
4. Use the existing PR-title/branch convention with the Jira key, and release tags
   following `vX.Y.Z[-rc.N]`. Prepare a timestamped `issue_tracker.fixture`
   export covering the relevant tickets and `blocked_by` links. **Live Jira is not
   connected**; if the snapshot is absent or stale, report missing business evidence
   honestly (NEEDS REVIEW / UNKNOWN as appropriate).
5. Open Claude Code in the library checkout. Start with
   `/library-release #<real-number>` or the full PR URL. Explain its STATUS,
   WHY and NEXT, then ask `why?`. If a blocker is confirmed, discuss the proposed
   release-content decision; do **not** claim runtime proof.
6. Optionally show `release-graph`, a read-only `release-mode preview`, or
   `release-report` (which writes only local report files). **Never use
   `--approve` in this demo.** Slack output is text to copy, not a message sent.

### Demo preflight checklist

- [ ] Real PR and Jira key selected; actual current PR head and relevant refs checked.
- [ ] Library and consumer repos accessible; config points to the correct clones.
- [ ] GitHub token has read-only permissions for the private resources being used.
- [ ] Live PR provider configured; **no** `pull_requests.snapshot`.
- [ ] Jira fixture exists, covers linked tickets and includes a usable freshness time;
      otherwise the limitation is disclosed explicitly.
- [ ] Tags, release candidates and selected services match the intended demonstration.
- [ ] Demo commands are read-only and no real workflow runs with `--approve`.
- [ ] Have the offline lab ready as a fallback if company access or network fails.

## Known limitations and safety boundaries

* Phase 1 is a **static and Git-evidence assessment**, not a runtime certification.
  Sandbox runtime investigation is planned for Phase 3, not available now.
* First runs on a new clone are colder; repeats benefit from immutable analysis caching.
  Measured Windows lab results: baseline **73.3 s** across 8 engine processes;
  Phase 1 cold **4.8 s**, warm **0.65 s**, with **118 / 22** Git subprocesses.
  See [performance evidence](performance.md). Claude's model response time is excluded.
* AST-based dependency analysis covers Python. Non-Python changes or uncaptured runtime
  behaviour must be labelled **unverified** rather than declared safe.
* Jira live integration remains future work; business links come from snapshots. The
  offline lab uses fixture PRs; a real PR needs correct GitHub access.
* Every release-content decision requires an explicit human choice. Every write is
  behind `--approve`. The default assessment never pushes, publishes, merges, deploys,
  changes Jira or sends Slack messages.
